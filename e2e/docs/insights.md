## Tool & Library Notes

- **2026-09-25 · `find <locator> click` reports `✓ Done` even when the target is scrolled out of the viewport and the click hits nothing — scroll it into view first, and know which container actually scrolls** — `specs/08-smart-diff.flow.json`'s `find text "Docs" click --exact` step kept exiting 0 while the Docs group never collapsed. The exact-match locator (see the entry below) really did resolve to the one true `<span>` — confirmed with `agent-browser eval "...getBoundingClientRect()"`, which showed the span at `top: 1107` while `window.innerHeight` was `577` — but the click never registered because this app scrolls inside `<main>` (`document.querySelector('main').scrollHeight` 1394 vs `clientHeight` 525), not `window` (`plain `agent-browser scroll down 2000` left `window.scrollY` at `0`, and `agent-browser scrollintoview "//span[...]"` no-opped too — its XPath resolution returned 0 matches via `agent-browser get count`, another silent-success case). The only thing that worked: `agent-browser scroll down 700 --selector main` (the `scroll` command's `-s/--selector` flag, for exactly this "not the window" case) — after that the span's rect fell inside the viewport and the same `find text "Docs" click --exact` worked immediately. Lesson: agent-browser's click/scroll/scrollintoview commands can all report success while doing nothing, so verify with `get count`/`eval getBoundingClientRect` rather than trusting the exit code — and check `document.querySelector('main').scrollHeight > clientHeight` (or similar) before assuming `window` is the scrollable element. (×1)
  Where: `specs/08-smart-diff.flow.json:13` (`scroll down 700 --selector main`), `../client/src/app/repos/[repoId]/pulls/[number]/_components/DiffTab/_components/DiffGroup/styles.ts` (the group whose header sits below the fold)

- **2026-09-25 · `find text "X" click` can silently click Next.js's inlined RSC data `<script>` instead of the real element — always add `--exact` for short/common text** — Next.js's App Router inlines the full flight payload (including every `next-intl` message string, e.g. all of `client/messages/en/*.json`) into a `<script>self.__next_f.push(...)</script>` tag with no children, so it passes agent-browser's "leaf element" test the same as any real text node. A non-exact `find text "Docs" click` against `specs/08-smart-diff.flow.json` matched two leaves — the real `<span>Docs</span>` header AND this script (whose huge JSON blob contains `"docsLabel":"Docs"` as a substring) — and resolved to the script. The command still reports `✓ Done` (a click event was dispatched on *some* element), but nothing visible happens: the script has no click handler and isn't inside the real component tree, so the assertion after it (waiting for the post-click UI state) times out with no useful error pointing at the real cause. Diagnosed by `agent-browser eval "Array.from(document.querySelectorAll('*')).filter(el=>el.children.length===0 && el.textContent.includes('Docs'))..."` — two matches, one `SPAN`, one `SCRIPT`. Fix: add `--exact` (`el.textContent.trim() === value`) to any `find text ... click` whose text is short/generic enough that it could appear as a substring inside another string on the page — the flight script means *any* translated string is a candidate substring collision, not just accidental ones. (×1)
  Where: `specs/08-smart-diff.flow.json:14` (`find text "Docs" click --exact`)

- **2026-09-25 · `wait --text` and `find text` read different DOM representations — they disagree on CSS-transformed text** — `wait --text "X"` polls `document.body.innerText`, which Chrome computes AFTER layout/CSS (including `text-transform`), so it only matches the visually-rendered casing. `find text "X"` (and `find text "X" click`) instead reads raw `el.textContent`, unaffected by CSS. A label whose translation string is `"Docs"` but is styled `text-transform: uppercase` renders as `"DOCS"` in `innerText` while its `textContent` stays `"Docs"` — so `wait --text "Docs"` times out even though the element is on the page and `find text "Docs"` finds it fine. This broke `specs/08-smart-diff.flow.json`'s Smart Diff group-header assertion; fixed by waiting on `"DOCS"` (the rendered form) while keeping the later `find text "Docs" click` step literal. `find role --name` is a third, distinct semantic: case-insensitive substring against the CDP accessibility-tree name. Before adding a `wait --text` assertion, grep the target component for `textTransform` and match the rendered casing, not the source string. (×1)
  Where: `specs/08-smart-diff.flow.json:12` (the `wait --text` step), `../client/src/app/repos/[repoId]/pulls/[number]/_components/DiffTab/_components/DiffGroup/styles.ts:16` (`textTransform: "uppercase"`)

## Recurring Errors & Fixes

- **2026-09-25 · `e2e:hermetic` hangs forever, silently, when ANY stale process already holds port 3100** — Symptom: the run produces no output at all and never exits; `ps` shows `bash ../scripts/e2e.sh` alive but burning no CPU, with a single child, `curl -fsS http://localhost:3100`, stuck for tens of minutes. Root cause: the readiness loop polls the port with `curl -fsS` and **no `--max-time`**, so if something is LISTENING but not answering HTTP — e.g. an orphaned `next dev -p 3100` from a previous session, which in this case had been up for 6 days and returned nothing at all — curl blocks indefinitely and the loop's retry budget never advances. The script never reports "port busy", because from its side the port looks alive. Fix: before blaming the suite, run `lsof -nP -iTCP:3100 -sTCP:LISTEN` and `curl -s -o /dev/null -w '%{http_code}' --max-time 5 http://localhost:3100` — a `000` means a squatter; kill it (`kill <pid>` plus its `next dev` / `pnpm exec` parents) and re-run. Same applies to the API port (default 3001, `${API_PORT}`), which has the identical unbounded-curl loop. (×1)
  Where: `../scripts/e2e.sh:33` (`WEB_PORT="${E2E_WEB_PORT:-3100}"`), `../scripts/e2e.sh:153` (the unbounded web `curl -fsS` readiness loop), `../scripts/e2e.sh:139` (the same shape for the API port)

- **2026-09-25 · Every flow failing with `spawn agent-browser ENOENT` means the CLI was never installed — it is NOT a package dependency** — All 8 flows fail identically and instantly, which reads like the suite is broken. It isn't: `e2e/package.json` declares only `tsx`, `typescript` and `@types/node`, so `npm install` in this package can never provide `agent-browser`. It is a GLOBAL, one-time prerequisite that also downloads Chrome for Testing — `npm i -g agent-browser && agent-browser install` (`README.md:52-53`) — and the runner shells out to whatever `AGENT_BROWSER_BIN` names (default `agent-browser`, resolved from `PATH`). Check with `which agent-browser` before concluding anything about the flows; a machine that has never installed it has never been able to run e2e at all, no matter how green the rest of the gates are. (×1)
  Where: `package.json` (`devDependencies` — no `agent-browser`), `README.md:52` (the global install line), `README.md:83` (`AGENT_BROWSER_BIN` override)
