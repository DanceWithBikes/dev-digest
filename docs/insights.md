## Codebase Patterns
- **2026-10-05 · SDD pipeline: fixing an `implemented` spec after Acceptance takes four hops, and its line anchors have to be re-resolved every time** — When `plan-verifier` (Acceptance) finds a criterion the shipped code meets differently and the user keeps the code, the order is: `spec-creator` rewrites the `AC-N` (the status goes back to `draft`, the tick and anchor are dropped) → the user sets `approved` → `doc-writer` re-anchors and sets `implemented` → `plan-verifier` again. SPEC-03 needed this twice in one day (AC-52, then AC-58/AC-86). The `path:line` anchors in specs drift silently: 20+ anchors in SPEC-03 were already 1–20 lines off two days after shipping, and inserting one test shifts every later anchor in that file. Tell `doc-writer` to re-resolve every anchor by symbol or test name on each spec touch, not only the ones it changed.
  Where: `docs/specs/pr-brief.md` (`## Changelog`, 2026-10-05 entries), `docs/plans/pr-brief/verification.md` (`## Verdict`)

- **2026-10-03 · SDD pipeline: any `spec-creator` edit to an approved spec, even a verbatim relocation of AC-N into a new module part, flips it back to draft** — The guard requires `Status: draft` in the result of every write, so the agent must change the header to draft before it can even move text. - **2026-09-24 · A `docs/specs/` file asserts test coverage per criterion, so writing one in PARALLEL with the tests guarantees it ships stale** — The house spec format makes every acceptance criterion carry its evidence: either `· test: path:line ("the it() name")` or an explicit `· untested` (see `docs/specs/cost-badge.md:11-13`). (Related: the spec format is also why `plan-verifier` can check coverage claims mechanically.)

## Tool & Library Notes
- **2026-10-03 · macOS BSD `sed -i -E '…' file` treats `-E` as the backup suffix and leaves a stray `file-E` copy next to the edited file** — On BSD sed, `-i` takes the next argument as the extension. `sed -i -E` therefore writes the edit and also leaves the pre-edit file as `<name>-E`. Grep and git status then show the old content, as with two `*.test.tsx-E` files left behind by a test-writer run on SPEC-03. Instead, use `sed -i '' -E '…'` on macOS, or the Edit tool. After any agent's `sed -i` run, check with `find . -name '*-E' -not -path '*/node_modules/*'`.
  Where: no code anchor — BSD `sed(1)` `-i extension`; found in `client/src/app/repos/[repoId]/pulls/[number]/_components/OverviewTab/` (removed)

- **2026-10-03 · zsh shell quirks that break chained gate commands: `echo ===X` and `${PIPESTATUS[0]}`** — a word starting with `=` is `=cmd` expansion in zsh, so `echo ===server` fails with `==server not found` and aborts a `&&` chain before the gate runs. Use `echo "-- server"` as the separator. Also, `${PIPESTATUS[0]}` is empty in zsh; read a gate's exit code through `| tail` with `${pipestatus[1]}` (lowercase, 1-based).
  Where: no code anchor — the Bash tool shell is zsh (`echo $SHELL`)

- **2026-10-03 · Claude Code transcripts: sum usage per `message.id`, and never trust the parent's `totalTokens`** — There are three traps when counting session cost from `~/.claude/projects/<slug>/`:
  - Every `assistant` record holds **one** content block and repeats the full `usage` of its message, so summing records counts tokens 2–3×. Dedupe by `message.id`.
  - The `toolUseResult.totalTokens` of an Agent call is the child's **last-turn context**, not its spend (real pr-self-review run: the parent saw 0.6M of 2.94M). Background agents report it only later, in a `<task-notification>` (`<subagent_tokens>`), and depth-2 agents never appear in the parent. Read `<session>/subagents/agent-*.jsonl` and use `parentAgentId`/`spawnDepth` from `*.meta.json`.
  - The slug replaces every non-alphanumeric char with `-` (`AI_Neoversity` → `AI-Neoversity`), not just `/`.
  - An Agent call the user rejected or interrupted has **no `agentId`**: its `toolUseResult` is the plain string `"User rejected tool use"` and the `tool_result` has `is_error: true`. The child's log still exists and its spend is real. Link it back through `meta.toolUseId` == the `tool_use_id`, otherwise the run looks like a success with unexplained cost (real case: 48f4a869, 1.80M lost).
  Where: `.claude/skills/workflow-retro/scripts/lib.mjs:77` (`assistantMessages`), `.claude/skills/workflow-retro/scripts/retro.mjs:102` (`notifications`), `.claude/skills/workflow-retro/scripts/retro.mjs:76` (`rejectedAgentCalls`)

- **2026-09-27 · An unset env var in an MCP header fails as "badly formatted", not "unauthorized" — and the `/mcp` panel shows only the URL's origin** — The `github` plugin server failed with `Error POSTing to endpoint: bad request: Authorization header is badly formatted`, and the panel displayed its URL as `https://api.githubcopilot.com`, which reads like a wrong endpoint. Both are misleading. (1) The panel truncates to the origin; the configured URL was already the correct `https://api.githubcopilot.com/mcp/`. Never diagnose an MCP URL from the panel — read the server's own config. (2) `${VAR}` in a `headers` value is substituted with no existence check, so an unset var sends a literal `Bearer ${GITHUB_PERSONAL_ACCESS_TOKEN}` — a *malformed header*, which is why the error says nothing about auth and sends you hunting the URL. Any `bad request` from an MCP server whose config interpolates a var: check the var is set before anything else. (3) The var must exist in the **environment Claude Code inherited at launch**; `/mcp` → Reconnect re-dials with the same process env, so a var exported after startup needs a full restart, not a reconnect.
