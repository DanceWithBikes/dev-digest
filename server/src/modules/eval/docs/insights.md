## Codebase Patterns
- **2026-10-07 · In `eval.it.test.ts` the seeded Security Reviewer accumulates cases from earlier tests; "the 8 seeded cases" must come from the seeded batch's runs** — The suite runs against one Postgres database seeded once; the one-click and CRUD tests add cases owned by the seeded agent and do not always delete them, so `select … from eval_cases where owner_id = <security agent>` returned 11 rows when the NFR-5 fixture expected 8. Derive the seeded case ids from `eval_runs where batch_id = <seeded batch with model 'seed'>` (always exactly 8), never from `eval_cases` by owner.
  Where: `../../../../test/eval.it.test.ts:801-802` (`seededRuns`, `expect(seededRuns).toHaveLength(8)`)
- **2026-10-07 · Any `buildApp` against the dev `DATABASE_URL` reaps EVERY `running` eval batch — so a real-model experiment and the server unit suite cannot overlap** — `reapOrphans` runs at boot and marks all `eval_batches.status = 'running'` rows `failed` ("server restarted while this batch was running"), not just the booting process's own. The server unit suite (`pnpm exec vitest run --exclude '**/*.it.test.ts'`), `scripts/verify.sh` (its server lane), `plan-verifier`/`pr-self-review` gate runs and `routes-smoke.test.ts` all call `buildApp` on the dev DB. Start a batch through the studio or `POST /agents/:id/eval-runs`, then run any of those → the batch is reported `failed` mid-flight and its cases stop being recorded. Sequence them: finish (or let fail) every experiment batch before gates, and never launch a reviewer subagent that runs gates while a batch is in `running`.
  Where: `../../../app.ts:91` (`makeEvalService(container, app.log).reapOrphans()`), `../service.ts:190` (`reapOrphans`)

## Tool & Library Notes
- **2026-10-07 · A real batch on `openrouter/deepseek/deepseek-v4-flash` takes ~2 minutes per case, so the 10-case Security Reviewer set is a ~20-minute batch and the 3-batch prompt experiment is about an hour** — the runner is sequential by design (frozen inputs, one `agent_runs`-style call per case), and the studio polls every 4 s, so the UI shows `running` with `cases_total` only; per-case progress is visible in `eval_runs` (`select count(*) from eval_runs where batch_id = …`). Plan model-backed experiments around this, and never start gates (see Codebase Patterns) in that window.
  Where: `../runner.ts` (`EvalBatchRunner.execute`, the sequential `for` over the frozen case ids), `../../../../../client/src/lib/hooks/evals.ts` (`POLL_MS`)
