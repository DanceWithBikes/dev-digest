## What Works

- **2026-09-28 · A run stuck in `running` from an MCP session: capture the server's stderr by driving `pnpm mcp` yourself** — Claude Code's `~/Library/Caches/claude-cli-nodejs/<project>/mcp-logs-devdigest/*.jsonl` only logs CLIENT events (tool called/completed), never the server's own stderr, so the executor's step log is invisible there. Spawn `pnpm --silent mcp`, write `initialize` + `notifications/initialized` + a `tools/call` as JSON lines to its stdin, and pipe stderr to a file — the `RunLogger` lines show exactly which step a run is parked in. `lsof -nP -a -p <pid> -i` + `nettop -p <pid> -L 1 -x` then tell a network stall from local work. Root cause found this way: `../../../reviewer-core/docs/insights.md` (OpenRouter deadline). Beware: editing `reviewer-core` restarts a `tsx watch` API, whose `reapStaleRuns` marks this process's in-flight runs `failed` with no error text.
  Where: `src/mcp.ts:6` (`mcpLogger` → stderr), `src/modules/reviews/run-executor.ts:79` (`new RunLogger`)

## Codebase Patterns

- **2026-09-28 · Never pass a `ReviewRecord` through a tool output whole — its nested `findings` bypasses every filter** — `get_findings` used to return `review` as-is, so `review.findings` carried every finding with full `rationale`/`suggestion` next to the filtered top-level `findings`: `min_severity`, `limit` and `concise` were all silently bypassed (found by a live Claude Code call, not by the 44 green tests — none asserted on `review`'s shape). Fixed by projecting to `ReviewHeader` (`ReviewRecord.omit({ findings: true })`); `test/mcp-tools.test.ts` now pins it. Any new tool that returns a review must use the header too, and any test must assert on `findings`, not `review.findings`.
  Where: `src/mcp/schemas.ts:82` (`ReviewHeader`), `src/mcp/tools/get-findings.ts:13` (`toHeader`)

## Tool & Library Notes

- **2026-09-28 · Inspector 2.x "Schema portability: 19 warnings" on `get_findings` are an SDK conversion artefact, not a bug in our schemas** — The SDK converts zod v3 schemas with `zod-to-json-schema` using HARD-CODED options (`strictUnions`, `pipeStrategy` only — nothing is configurable from `registerTool`), which emits a nullable primitive (`z.string().nullable()`) as `"type": ["string","null"]`. Inspector flags that as less portable (Gemini's OpenAPI subset / OpenAPI 3.0 have no type arrays). All 19 are in `get_findings`'s OUTPUT schema (`run`, `review`, finding timestamps); every tool's INPUT schema — the part a client hands to the model — is clean. `outputSchema` is only used by the MCP client to validate `structuredContent`, and Claude Code / Desktop / Cursor accept type arrays, so this is accepted as-is. The `$ref`s in `list_agents`/`get_findings` output schemas come from the same converter deduplicating fields shared by the concise and full projections — legal, not flagged. Fix paths if a target client ever chokes: build MCP output schemas with `zod/v4` (its `toJSONSchema` emits `anyOf`) at the cost of duplicating `@devdigest/shared` v3 contracts; do NOT override the `tools/list` handler to rewrite schemas (couples to SDK internals).
  Where: `node_modules/@modelcontextprotocol/sdk/dist/esm/server/zod-json-schema-compat.js:27` (`zodToJsonSchema(schema, {...})`), `node_modules/@modelcontextprotocol/sdk/dist/esm/server/mcp.js:91` (`toolDefinition.outputSchema`), `src/mcp/schemas.ts:93` (`GetFindingsOutput`)

- **2026-09-28 · MCP Inspector is pinned to v1.0.2 because 2.x needs Node ≥22.19** — `@modelcontextprotocol/inspector@2.8.0` declares `engines.node >=22.19.0` (and pulls `undici@8`, same floor); this machine runs Node 22.17, so the user chose the deprecated-but-working v1 line (security fixes only) over a Node upgrade. v1's `--cli` mode is handy for scripted checks: `PATH="$PWD/node_modules/.bin:$PATH" npx -y @modelcontextprotocol/inspector@1.0.2 --cli tsx src/mcp.ts --method tools/call --tool-name list_agents`. Once Node ≥22.19 is the baseline, bump the pin to 2.x (its CLI changed: mode flags `--web`/`--cli`/`--tui` must come first).
  **Correction (2026-09-28):** Node upgraded to 22.23.3 (official nodejs.org `.pkg` in `/usr/local/bin` — nvm exists in `~/.nvm` but is not sourced by any shell profile, so it is NOT what Claude Code or `.mcp.json` run) and the pin moved to `2.8.0`. 2.x takes `--config <file> --server <name>`, so `mcp:inspect` now reads the launch command from the root `.mcp.json` instead of duplicating it; `--cwd ..` is required because that config's `pnpm --dir server` is relative to the repo root. Scripted check: `npx -y @modelcontextprotocol/inspector@2.8.0 --cli --config ../.mcp.json --server devdigest --cwd .. --method tools/list`.
  **Correction (2026-09-28):** `--cwd ..` works in `--cli` mode but the `--web` UI IGNORES it for a server loaded from `--config` — it spawns the command in the inspector's own cwd, so run from `server/` it failed with `canonicalizing the --dir argument: server → No such file or directory`. `mcp:inspect` therefore does `cd .. &&` first and launches from the repo root (the cwd `.mcp.json` assumes). Also: `--server` is a no-op in web mode ("lists every server in the file").
  Where: `package.json:19` (`"mcp:inspect"`)

- **2026-09-28 · A code change under `src/mcp/` is invisible to the running Claude Code session until `/mcp` reconnect** — `pnpm mcp` is plain `tsx src/mcp.ts` (no watch, by design — see AGENTS.md), and Claude Code keeps the stdio child alive for the whole session. After editing a tool, unit tests see the new code but a live `mcp__devdigest__*` call still runs the old one. Reconnect the `devdigest` server via `/mcp` (or restart Claude Code) before re-verifying by hand.
  Where: `package.json:18` (`"mcp": "tsx src/mcp.ts"`)

- **2026-09-28 · `@modelcontextprotocol/sdk@1.30.1`: three things that aren't obvious from the public types** — (1) `registerTool`'s `inputSchema`/`outputSchema` accept EITHER a raw shape (`Record<string, ZodType>`, e.g. `{ run_id: z.string().uuid() }`) OR a full `z.object(...)` — both normalize the same way (`zod-compat.js#normalizeObjectSchema`), so `schemas.ts` uses raw shapes for inputs (they read like a route's params) and full objects for outputs (so they can be composed with `.omit()`/`z.union()`). (2) `validateToolOutput` returns immediately when `result.isError` is true (`server/mcp.js:193`, `if (result.isError) { return; }`) — an output schema is declared but NEVER checked on an error result. This is what makes `get_blast_radius`'s stub safe: it declares `outputSchema: BlastRadius` for the future real implementation while its handler only ever returns `isError: true` with no `structuredContent`. (3) `InMemoryTransport` (used by the SDK's own test suite and by `test/mcp-tools.test.ts` here) lives at the PACKAGE ROOT (`@modelcontextprotocol/sdk/inMemory.js`), not under `/server` or `/client` like everything else — easy to miss since every other transport (`stdio.js`, `streamableHttp.js`) is under `/server`.
  Where: `node_modules/@modelcontextprotocol/sdk/dist/esm/server/mcp.js:185` (`validateToolOutput`), `node_modules/@modelcontextprotocol/sdk/dist/esm/server/zod-compat.d.ts:34` (`normalizeObjectSchema`), `node_modules/@modelcontextprotocol/sdk/dist/esm/inMemory.d.ts:1`, `src/mcp/tools/get-blast-radius.ts` (the stub that relies on (2))

- **2026-09-28 · A hand-written `{content, isError}` type for a tool's error result fails `pnpm typecheck` against `registerTool`'s callback signature** — `ToolCallback`'s return type is the SDK's own `CallToolResult` (a zod-`Infer`'d type with an index signature, `[x: string]: unknown`), not a plain object literal type. A custom `interface ToolErrorResult { content: {...}[]; isError: true }` is structurally close but MISSING that index signature, so TS rejects every tool handler with "Index signature for type 'string' is missing". Fix: import the type itself — `import type { CallToolResult } from '@modelcontextprotocol/sdk/types.js'` — and declare `export type ToolErrorResult = CallToolResult & { isError: true }` instead of inventing the shape.
  Where: `src/mcp/errors.ts:1` (the import), `node_modules/@modelcontextprotocol/sdk/dist/esm/types.d.ts:8089` (`CallToolResult = Infer<typeof CallToolResultSchema>`)

- **2026-09-28 · zod 3.25.76 (not 3.24.x) is required, and it is a NON-breaking bump already sitting in the lockfile** — The SDK's peer range is `^3.25 || ^4.0`; `server/package.json` pinned `^3.24.1` but `pnpm-lock.yaml` had already resolved `zod@3.25.76` transitively (some other dependency wanted it), confirmed live: `require('zod/package.json').version` → `3.25.76`. Bumping the specifier to `^3.25.76` and re-running `pnpm install --no-frozen-lockfile` (the repo's `--frozen-lockfile`-by-default install rejects an out-of-sync specifier) changed ZERO resolved versions — only the lockfile's `specifiers:` line. The SDK imports `zod/v3` internally (`import type * as z3 from 'zod/v3'`), which only exists from 3.25 onward (zod's v3→v4 compat shim); a real 3.24 install would fail to resolve that import.
  Where: `server/package.json:42` (`"zod": "^3.25.76"`), `server/pnpm-lock.yaml:77` (`zod: specifier: ^3.25.76, version: 3.25.76`), `node_modules/@modelcontextprotocol/sdk/dist/esm/server/zod-compat.d.ts:1` (`import type * as z3 from 'zod/v3'`)

## Open Questions

- **2026-09-28 · No MCP tool can find "the latest run" — `get_findings` needs a `run_id` only `run_agent_on_pr` hands out** — Asked "which findings did the last run produce?" in a fresh session, there is no `list_runs` / `get_latest_run` tool, so a run started from the studio (or an earlier MCP session) is unreachable through MCP. Workaround used: `docker compose exec -T postgres psql -U devdigest -d devdigest -c "select id, status, ran_at, findings_count from agent_runs order by ran_at desc limit 3"`, then `get_findings` with that id. Note the timestamp column is `ran_at`, not `created_at`. Open: add a workspace-scoped `list_runs` tool (filter by PR / agent, newest first)? Owner: MCP surface.
  Where: `src/mcp/schemas.ts:86` (`run_id: z.string().uuid()` — the required input), `src/db/schema/runs.ts:15` (`ranAt`)

- **2026-09-28 · No input-size guard before a single-pass review** — Security Reviewer on PR #10 (~20.8k added lines, 124 files) failed after ~72s with `OpenRouter returned no choices for Review: Input too long: 1511763 input tokens, limit is 1048576 for this model`.   Where: `src/modules/reviews/constants.ts:12` (`REVIEW_STRATEGY`)
