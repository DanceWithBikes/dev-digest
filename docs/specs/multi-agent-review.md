# Spec: Multi-Agent Review

Spec ID: SPEC-05
Status: implemented
Supersedes: —
Introduced in: L07

## Problem & user

One pull request can carry a security hole, a performance regression and a domain-rule violation at the same time, and no single reviewer agent covers all three. Today a reviewer in the studio can run one agent or "all enabled agents" on a PR, but cannot pick a subset. The agents then run one after another, so the wait is the sum of their times. Their findings land in one flat list per run, with no link between the runs of one launch. When two agents flag the same line, the reviewer sees two cards and has to spot the duplicate alone. When one agent flags a line and another stays silent, nothing shows the disagreement. Nothing estimates the time or cost before the reviewer clicks Run.

## Goals / Non-goals

Goals:
- A reviewer picks any subset of agents for one PR, sees a time and cost estimate from past runs, and launches them in one action.
- The selected agents run concurrently, so the wait is close to the slowest agent, not the sum. One agent's failure never stops the others.
- Every launch is one parent run that the reviewer can reopen later, with status, total time and total cost visible.
- Findings that several agents raised about the same code are shown together. Every original finding and the agent that produced it stay visible and actionable.
- For each code location, the reviewer sees what every selected agent said, including "did not flag", and can filter to locations where the agents disagree.
- The reviewer acts on findings (Accept, Dismiss, Learn, Turn into eval case) from the results page.

Non-goals:
- A reason text for "did not flag". It would need a reviewer-core output change or an extra model call per agent and location.
- Consuming the Learn decision (a memory store, prompt injection of learned findings). This spec only records the decision.
- Reply to author, and the "Compose review" button from the PR page mockup.
- Re-running one failed agent inside an existing parent run. A new launch creates a new parent.
- Including CI runs (`agent_runs.source = ci`) in a multi-agent run. Local runs only.
- Any change to the CI runner (`agent-runner/`) or to a server `ci` module.
- Sidebar entries for Memory, Agent Performance or CI Runs. Those pages do not exist.
- A merged "consensus" finding that replaces the originals, or a stored group record.
- Running agents in separate git worktrees. Agents run in-process.
- Parallelising the chunks inside one agent's review (reviewer-core map-reduce stays sequential).

## User stories

- US-1: As a reviewer in the studio, I want to tick the agents I want from the PR page and launch them in one click, so that I get specialised coverage without running each agent separately.
- US-2: As a reviewer in the studio, I want a Configure run screen with a time and cost estimate per agent, so that I know what a launch will cost before I start it.
- US-3: As a reviewer in the studio, I want the selected agents to run at the same time and to see each one's live status, so that I wait for the slowest agent, not for all of them in turn.
- US-4: As a reviewer in the studio, I want findings about the same code from different agents shown together with their authors, so that I do not read the same problem twice and still know who raised it.
- US-5: As a reviewer in the studio, I want to see, per code location, which agents flagged it and which did not, so that I can judge disagreements instead of missing them.
- US-6: As a reviewer in the studio, I want to Accept, Dismiss, Learn from or turn into an eval case any individual finding of a multi-agent run, so that my decisions feed the same data as single-agent reviews.
- US-7: As a reviewer in the studio, I want to reopen earlier multi-agent runs from a list, so that I can return to a result without re-running it.
- US-8: As an agent calling the MCP server, I want review runs to use the same concurrent executor, so that my reviews finish as fast as studio reviews.

## Edge cases

- The same agent id is listed twice in `agentIds`: one run is created for it (AC-13).
- `agentIds` together with `agentId` or `all`: undecided, see OQ-1.
- A single agent is checked in the popover: the launch still creates a parent run and opens the results page with one column (AC-14, AC-67).
- More than 4 agents are selected: agents 5 and 6 stay `queued` until a slot frees (AC-20, AC-22). Their columns show the status "Waiting for a free slot…" without a live log. Each live log holds one of the browser's 6 HTTP/1.1 connections and the executor runs at most 4 agents at once, so a column opens its stream only when its run starts; the server replays the run's event buffer to that late subscriber, so no line is lost (AC-98, NFR-1, NFR-7).
- The workspace has more than 6 enabled agents: the popover and Step 2 pre-check the first 6 enabled agents in list order, and "Select all" stops at 6. Once 6 are checked, every unchecked row or card is non-operable and the hint "Up to 6 agents per run" is shown until one is unchecked. The studio therefore never sends more than the 6 ids the API accepts (AC-17, AC-62, AC-63, AC-77, AC-78, AC-82).
- The PR diff cannot be loaded: every child fails, the parent is `failed` (AC-24, AC-36), and every take is `no_result` (AC-56).
- A child run is cancelled while queued: it counts as settled. The parent becomes `partial` or `failed` once the rest settle (AC-36, AC-37).
- The server restarts mid-run: the boot reaper marks in-flight children `failed`, so the parent settles to `partial` or `failed`. Status is derived on read, so no parent row is left stuck.
- A child has no recorded cost (provider returned no usage, or it is still running): the total covers only known costs and is labelled "partial" (AC-39, AC-92).
- Total duration while the parent is still running: measured to the latest finish so far. The value grows until the parent settles (AC-40).
- One agent produces two findings that match each other: both join the same group, and that agent's take shows its most severe member (AC-42, AC-54).
- A group is flagged by every selected agent with the same severity: not a conflict, so it is hidden while "Show only conflicts" is on (AC-51, AC-52, AC-112).
- Agent A has a CRITICAL and a WARNING member in a group, agent B has one CRITICAL member, and no other selected agent is silent: both takes read CRITICAL, so the group is not a conflict. Severities are compared per take verdict, not per member (AC-52, AC-54).
- Every selected agent returns zero findings: there are no location groups, and the section shows the "No conflicts" text (AC-116).
- An agent was deleted after the launch: its runs keep a null agent. The column shows the run with the placeholder "Deleted agent" (`client/messages/en/runs.json:153`) instead of an agent name, and its takes still appear by run order. No dedicated criterion.
- An agent has runs only on an older model: it has no estimate (AC-60, AC-81).
- The PR has no stored patches and no clone: `loadDiff` throws `no diff available (...)` (`server/src/modules/reviews/diff-loader.ts:33`), so every run of the launch fails with that error and the parent is `failed` (AC-24, AC-36). Before this feature the agents reviewed an empty diff and finished `done` with no findings. This applies to seed PR #482 (`server/src/modules/reviews/docs/insights.md:37`), which the mockups use. The e2e flow therefore does not launch agents. It opens a seeded finished parent run on PR #484 instead (AC-123, AC-125).
- Configure run is opened with no active repository: the Step 1 list is empty and the run button stays disabled (AC-72, AC-84).
- Turn into eval case after only Learn: stays disabled, because Learn is not accept or dismiss (AC-110). See OQ-3.

## Untrusted inputs

- `agentIds` / `agentId` / `all` (studio user or MCP caller). Threats: running another workspace's agent, and an oversized fan-out that multiplies model cost. Neutralised by AC-16 (workspace check, 404, nothing created), AC-17 (1–6 ids) and AC-20 (concurrency cap). Mixed fields: OQ-1.
- Parent run id (path parameter and results URL). Threat: reading another workspace's results. Neutralised by AC-33 and AC-94.
- Finding id in `POST /findings/:id/learn`. Threat: deciding on another workspace's finding. Neutralised by AC-27.
- `pr` query parameter. Threat: a crafted id pointing at a PR outside the active repository. Neutralised by AC-74.
- `view` query parameter. Threat: an unknown value breaking the page. Neutralised by AC-93.
- Finding title, rationale, suggestion and run summary (LLM output). Threats: script or markdown injection into the studio, and instructions planted in the diff and echoed by the model. Neutralised by AC-122 (same markdown renderer as the PR page, titles as plain text) and AC-57 (no model call consumes them again).
- PR title (GitHub). Threat: script injection into the results subheader and index. Neutralised by AC-122.
- PR diff (clone or patches). Threat: prompt injection into the review prompt. Handled unchanged by the existing reviewer-core guard. This spec adds no new prompt path, and AC-57 adds no model call.
