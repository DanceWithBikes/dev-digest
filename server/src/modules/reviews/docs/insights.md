## Codebase Patterns

- **2026-09-24 · Missing-context is the honesty signal; sources infrastructure gathers full materials but keeps them private** — The Intent Layer's three-phase architecture (collect → classify → derive) is strict about data flow: the collector gathers full materials (`issue.title`, `issue.body`, `spec.text` - the actual documents), but the public API only exposes metadata (`sources: [{kind, ref, ok}]`) and an honesty field (`missing_context[]` — sources that failed to resolve). This separation is intentional: (a) on success, the LLM consumed the materials and returned scope bullets; the raw content is redundant for the UI, which only needs to know which sources resolved (b) on failure, `missing_context[]` tells the user precisely which references the system tried and failed to fetch, triggering a re-run or manual fix. A future feature might expose sources content in the API (e.g., an "expand sources" detail panel in the Intent card), and the data collection infrastructure is already there — just not exposed in `PrIntentRecord`. Consequence: if you add a new source kind (e.g., linked wiki pages), the collector's `collect()` function is the right place to fetch and cache the materials; the UI can always see them later without changing classifier or repository code.
  Where: `ports.ts:92` (`collect` returns full `GatheredIntentSources`), `ports.ts:13` (`IntentSource` — metadata only), `server/src/vendor/shared/contracts/review-api.ts:76` (`sources: IntentSource[]`, `missing_context: string[]`), `compose.ts:66` / `compose.ts:89` (`resolveIssue` / `resolveSpec` fetch full bodies and cache them), `run-executor.ts:462` (only `sources.attempts` persisted as metadata)

- **2026-09-24 · `git.readFile` ignores the PR's `head_sha` entirely — it reads the clone's current working-tree file** — `SimpleGitClient.readFile` is `readFile(join(this.clonePathFor(repo), path), 'utf8')` — no `git show <sha>:path`, no checkout, no ref argument at all. So a linked spec resolves (or doesn't) based on whatever is physically checked out on disk in `server/clones/<owner>/<repo>/` at call time, NOT the specific commit the PR was opened against. Two consequences: (a) testing/demoing spec resolution for an old PR works fine even though it's "wrong" (reads today's file, not the PR-era file) — don't be surprised the content doesn't match the PR's actual diff; (b) if the local clone is stale (not `git pull`ed since some doc was added upstream), `resolveSpec` fails with a perfectly valid-looking spec path — the fix is refreshing the clone, not the code.
  Where: `server/src/adapters/git/simple-git.ts:129` (`readFile`), `server/src/adapters/git/simple-git.ts:37` (`clonePathFor`), `server/src/modules/reviews/compose.ts:96` (the only caller, `resolveSpec`)

- **2026-09-24 · "The classifier never sees diff bodies" is enforced by the PORT'S TYPE, not by discipline — keep it that way** — `UnifiedDiff` is `{ raw: string; files: [...] }` and `raw` is the ENTIRE diff text, so any function handed a `UnifiedDiff` can leak whole file contents into a prompt. The Intent Layer's guarantee is structural instead of documentary: `IntentSourceCollector.collect` takes `IntentDiffFiles` (`{ files: { path, hunks: {oldStart,oldLines,newStart,newLines}[] }[] }`), which has no `raw` at all, and the single call site passes a fresh literal `{ files: diff.files }`. Because that is an object literal, TS excess-property checking also rejects a later `{ ...diff }` shortcut — the leak becomes a compile error, not a review miss. Two things follow: (a) never "simplify" the signature to accept `UnifiedDiff` just because the caller has one (structural typing makes it assignable, which is exactly the trap); (b) hunk header TEXT is not available anywhere — `adapters/git/diff-parser.ts` keeps only the numbers, so `intent-sources.ts#renderHunkHeader` re-renders `@@ -a,b +c,d @@` from them.
  Where: `ports.ts:38` (`IntentDiffFile`), `ports.ts:51` (`IntentDiffFiles` — no `raw`), `ports.ts:92` (`collect` signature), `run-executor.ts:452` (`{ files: diff.files }` — the only call site), `../../../vendor/shared/adapters.ts:186` (`UnifiedDiff.raw`)

- **2026-09-24 · Need another module's TABLE? Query it from your own repository — do NOT look for a `container.<m>Repo`** — `modules/AGENTS.md` says "never import another module's folder — shared pieces come from `container`", which reads as "there is a container getter for every module's repository". There is not: `container` exposes `agentsRepo`, `reviewRepo`, `skillsRepo`, `repoIntel` and nothing else — notably **no `pullsRepo`**, even though `pulls` owns `pull_requests`, `pr_files` and `pr_commits`, which reviews reads constantly. The resolution is the ring rule, not a new getter: `only-repositories-touch-the-database` scopes on the *layer*, not the table owner, so a module's own `repository.ts` may SELECT from any table. L03's Intent Layer needed commit messages and added `commitsForPull` to the reviews repository rather than reaching for `pulls/repository.ts` (which `no-cross-module-imports` would have rejected) or adding a container getter (which nothing else wants). `db/AGENTS.md`'s "don't edit shared schema tables" restricts *writing/migrating* another module's tables, not reading them. Rule of thumb: cross-module **behaviour** goes through a container port; cross-module **data** is just a query in your own repository.
  Where: `repository/pull.repo.ts:115` (`commitsForPull`), `repository.ts:142` (facade), `../../../platform/container.ts:99` (`agentsRepo` — note the absent `pullsRepo` beside it), `../../../.dependency-cruiser.cjs:126` (`no-cross-module-imports`)

## Tool & Library Notes

- **2026-09-24 · `deepseek/deepseek-v4-flash` answers in Chinese when the prompt gives it no language and the input is sparse (fixed)** — The intent classifier's `SYSTEM_PROMPT` told the model what to return but never in what language; the main review prompt never had this problem because its input (code/diff) is already English and anchors the model, but the intent classifier's input can be nearly empty (an unreadable/empty PR body, e.g. observed live on PR #7 "L1: fix mentor comments"), and without an anchor the default classifier model answered in Chinese for `intent`/`in_scope`. Fixed by adding an explicit `Always answer in English, regardless of the language used in the PR title, description, linked issue, or spec.` line to `SYSTEM_PROMPT`, pinned by a unit test. Anyone writing a free-text (non-schema-enum) LLM prompt in this codebase should state the output language explicitly rather than relying on the input's language to anchor it — especially for models origin-biased toward a non-English default.
  Where: `intent-prompt.ts:29` (`SYSTEM_PROMPT`), `intent-prompt.ts:39` (the new language line), `server/test/reviews-intent-sources.test.ts` (`describe('SYSTEM_PROMPT')`), `compose.ts:114` (`review_intent` feature-model slot, defaults to `deepseek/deepseek-v4-flash`)
