## What Doesn't Work

- **2026-09-21 · `pnpm db:generate` blocks forever when one table both gains and loses a column — split it into two generates** — Reworking `conventions` (adding `category`/`evidence_line`/`status`/`created_at`, dropping `accepted`) made drizzle-kit ask `Is category column created or renamed from another column?` and wait on an interactive select. Tried: piping answers (`printf '\n\n\n' | pnpm db:generate`, `yes '' |`) → Failed because: drizzle-kit reads the keypress from the TTY, not stdin, so the prompt simply never advances and the command hangs with no migration written. Instead: make the change additive first — keep the doomed column in `schema/<domain>.ts`, run `db:generate` (pure ADDs, no prompt), then delete the column and run `db:generate` again (pure DROP, no prompt). That produced `0011_dark_reaper.sql` + `0012_sparkling_thena.sql` with no interaction. The prompt only appears when adds and drops land on the same table in the same diff, so it is worth splitting even when you are sure of the answer.
  Where: `src/db/schema/knowledge.ts:31` (`conventions`), `src/db/migrations/0011_dark_reaper.sql:1` (the ADDs), `src/db/migrations/0012_sparkling_thena.sql:1` (the DROP), `package.json` (`db:generate`)

## Codebase Patterns

- **2026-09-22 · `src/db/rows.ts` looks like the sanctioned way to share row types — reaching for it from a service ADDS an arch violation** — Its doc comment invites cross-cutting consumers to use it "WITHOUT importing another module's data layer", which reads like the approved escape hatch. But `only-repositories-touch-the-database` forbids all of `src/db/**` outside a repository, `import type` included, so `rows.ts` is exactly as forbidden as `schema.ts` — `reviews/service.ts` is in the baseline for precisely this import, and it is the trap a new module falls into first. What rows.ts is actually for: one repository re-exporting its own row (`conventions/repository.ts` does `export type { ConventionRow }`) so its public type API survives. For anything crossing into a service, declare the shape in the module's `domain.ts` and have the repository `select` those columns by name — the L02 refactor of `pulls` did this and the module left the baseline entirely. Selecting `*` and casting would have compiled just as well and kept the coupling.
  Where: `src/db/rows.ts:18` (`PullRow` — tempting, wrong from a service), `src/modules/reviews/service.ts:4` (`import type { AgentRow }` — the baselined example), `src/modules/pulls/domain.ts:18` (`PullRecord` — the shape to copy), `src/modules/pulls/repository.ts:25` (`PULL_COLUMNS` — named columns, so the domain type is checked rather than asserted)

- **2026-09-21 · `seed.ts` is idempotent by NAME, so editing a seeded body never reaches an existing workspace** — Every seeder here is "select by `(workspaceId, name)`, insert only if missing". That keeps re-running `dev.sh` safe, but it means a row that already exists is never updated: when L02 added the full `test-coverage-rubric` body, a throwaway 72-char skill with that same name (created earlier by curl) survived the seed, and the demo silently ran on the stub. Nothing errors — the only symptom is a body that is too short. So: after changing a prompt or skill body in `seed-prompts.ts` / `seed-skills.ts`, either delete the existing row first (`DELETE /skills/:id`, `DELETE /agents/:id` — links cascade) or verify the length of what actually landed; `pnpm db:seed` alone proves nothing. The same applies to the built-in agent prompts, which is why `seed-prompts.ts` already warns that editing a prompt "only affects freshly seeded workspaces".
  Where: `src/db/seed.ts:339` (`seedSkills`), `src/db/seed.ts:377` (`if (!row)` — the insert-only branch), `src/db/seed-prompts.ts:7` (the same caveat for agent prompts)

- **2026-09-21 · `DiffHunk` has no line content — only line numbers; the text lives in `UnifiedDiff.raw`** — A natural-looking `hunk.lines.filter(l => l.kind === 'add')` compiles to `undefined` at runtime and fails with `Cannot read properties of undefined (reading 'kind')`. `DiffHunk` is `{ file, oldStart, oldLines, newStart, newLines, newLineNumbers }` — `newLineNumbers` exists for grounding (which line numbers a finding may cite), not for reading code. To assert on added/removed text, split `diff.raw` and filter on the `+`/`-` prefix, excluding the `+++`/`---` headers.
  Where: `src/vendor/shared/adapters.ts:175` (`DiffHunk`), `src/vendor/shared/adapters.ts:182` (`newLineNumbers`), example: `test/seed-fixtures.test.ts:46` (`linesOf`)

- **2026-09-20 · The `routes → service → repository` layering is convention-only, and half the modules skip it** — Nothing enforces module layering: no ESLint, no dependency-cruiser config, no CI gate (`dependency-cruiser` in `package.json` is a runtime library for repo-intel, not a linter). Only `repos`, `agents`, `reviews` and `repo-intel` actually have a service + repository; `pulls`, `settings`, `polling` and `workspace` import `drizzle-orm` and the schema barrel straight into `routes.ts` and query inside handlers. The "tiny modules may live in a single `routes.ts`" allowance was written for `polling`/`workspace`, but `pulls/routes.ts` grew to ~360 lines under it. So don't copy `pulls` or `settings` as a template for a new module — copy `repos` — and any route file that needs a Drizzle import should get a `repository.ts` instead. A mechanical import-boundary check (dependency-cruiser `forbidden` rules with a baseline for the four files above) is planned alongside a `backend-onion-architecture` skill.
  Where: `src/modules/AGENTS.md:10` (the "Tiny modules" allowance), `src/modules/pulls/routes.ts:3` (`from 'drizzle-orm'`) / `:6` (`db/schema.js`), `src/modules/settings/routes.ts:3` / `:10`, `src/modules/polling/routes.ts:3`, `src/modules/workspace/routes.ts:2`; clean reference: `src/modules/repos/repository.ts:20` (`RepoRepository`)
  **Update (2026-09-21):** shipped — `.dependency-cruiser.cjs` (13 rules), `pnpm arch:check` / `arch:all` / `arch:baseline`, a CI step in the `typecheck` job, and `.dependency-cruiser-known-violations.json` holding the 43 pre-existing violations. `pnpm arch:check` now passes and fails on any NEW wrong-way import (verified with a throwaway file). Two rules found more than the manual survey did: `services-take-ports-not-the-container` (9 hits — every service takes the whole `Container`) and, thanks to `tsPreCompilationDeps: true`, type-only leaks of Drizzle row types into `reviews/service.ts` and `repos/helpers.ts`. Rationale per rule: `.claude/skills/backend-onion-architecture/references/enforcement.md`.

- **2026-09-21 · `server/package.json` is NOT skip-worktree — TESTING.md says it is** — `TESTING.md:83` states the file is `skip-worktree` with a diverging local variant, and `.github/workflows/server-unit.yml` inlines `pnpm exec vitest run …` rather than calling a script because of it. `git ls-files -v server/package.json` returns **`H`** (normal); a skip-worktree file would return a lowercase `S`. Edits to it do show up in `git diff` (verified by adding the `arch:*` scripts). So new scripts CAN be added and committed normally — but keep CI inlining its commands anyway: the workflow comments cite the stale reason, and quietly switching CI to `pnpm arch:check` would break if anyone re-sets the bit locally.
  Where: `TESTING.md:83` (the stale claim), `server/package.json:12` (`arch:check`, added and committed fine), `.github/workflows/server-unit.yml:72` (the inlined architecture step)

- **2026-09-19 · The "no-DB" unit suite writes to your dev DB — don't run it while a review is in flight** — `test/routes-smoke.test.ts` claims its routes "don't touch the database", but it calls `buildApp({ config })` without a `db`, so `buildApp` opens `DATABASE_URL` from `server/.env` and, on boot, reaps every `agent_runs` row still `running` → `failed` (all workspaces). With the dev Postgres up, `pnpm exec vitest run --exclude '**/*.it.test.ts'` therefore kills any review you started in the studio. Without Docker it just logs "stale-run reaping failed (non-fatal)". Instead: wait for runs to settle before running unit tests, or run them with `DATABASE_URL` pointed at a throwaway DB.
  Where: `test/routes-smoke.test.ts:7` (the "No-DB" claim), `test/routes-smoke.test.ts:15` (`buildApp({ config })`), `src/app.ts:43` (`createDb(config.databaseUrl)` when no `opts.db`), `src/app.ts:81` (`reapStaleRuns` on boot)

## Tool & Library Notes

- **2026-09-24 · `domain-files-are-pure` only checks files DIRECTLY under `src/modules/<m>/` — a nested `<module>/<sub>/helpers.ts` looks pure and is never gated** — The rule's `from.path` is `${MODULE}(domain|ports|helpers|constants)\.ts$` where `MODULE = '^src/modules/[^/]+/'`, and `[^/]+` cannot cross a slash. So `modules/reviews/helpers.ts` is forbidden from importing the container, db, adapters and framework — but `modules/reviews/intent/helpers.ts` matches nothing and may import all of them with `pnpm arch:check` still green. Nothing in any `AGENTS.md` says this, and the natural reading ("helpers.ts is pure") is wrong one directory down. Two consequences: (a) when a feature needs several pure files in one module, keep them FLAT with a prefix (`intent-helpers.ts`, `intent-prompt.ts`) rather than grouping them in a subfolder — that is why L03's Intent Layer files are laid out that way; (b) if you do create a subfolder, its purity is a code-review item, not a machine-checked one. The coarser rules still bind either way (`only-repositories-touch-the-database`, `application-has-no-direct-io`, `only-routes-know-fastify`, `no-cross-module-imports`) because those match on the bare module prefix — so nothing illegal is *possible* in a subfolder, it is just the domain-ring purity that goes unenforced.
  Where: `.dependency-cruiser.cjs:16` (`MODULE`), `.dependency-cruiser.cjs:100` (`domain-files-are-pure`), `.dependency-cruiser.cjs:105` (`from: { path: \`${MODULE}(domain|ports|helpers|constants)\\.ts$\` }`), `src/modules/reviews/ports.ts` (a file the rule DOES cover — it may not import `Container`)
  **Correction (2026-09-24): the "keep them FLAT with a prefix" advice above is WRONG — a prefixed name is just as unchecked as a nested one.** The alternation is anchored immediately after `[^/]+/`, so the rule matches **exact filenames only**. Executed against real paths: `reviews/ports.ts` COVERED, `reviews/helpers.ts` COVERED, `reviews/intent-helpers.ts` **NOT** covered, `reviews/intent/helpers.ts` NOT covered. So `helpers` appearing in a filename is no signal that the purity gate applies, and L03's flat layout bought zero machine coverage over a subfolder — the files are pure by discipline, not by gate. What IS still enforced on any file under `src/modules/<m>/` (flat or nested): `only-repositories-touch-the-database` (`:40`), `only-routes-know-fastify` (`:52`), `modules-depend-on-ports-not-adapters` (`:67`), `services-take-ports-not-the-container` (`:76`), `application-has-no-direct-io` (`:89`). What is LOST outside the exact four names: the ban on importing `^src/platform/(?!errors\.ts$)` and on `(routes|service|repository)` — i.e. an `intent-helpers.ts` may import `./service.js` or `platform/run-logger.ts` with the gate still green. The one name that genuinely matters is `ports.ts`: it IS covered, so it must never import `Container`.
  Where: `.dependency-cruiser.cjs:105` (exact-filename alternation), `src/modules/reviews/intent-helpers.ts` (pure, but unenforced), `src/modules/reviews/AGENTS.md:12` (claims purity — true by discipline only)

- **2026-09-21 · Drizzle's `text('col', { enum: [...] })` is a TypeScript narrowing only — widening one needs NO migration** — `0000_init.sql` emits plain `"source" text NOT NULL` for these columns: no pg enum, no CHECK constraint. So adding a value (L02 added `imported_file` to `skills.source`) is a one-line schema edit plus the matching `z.enum` in BOTH `vendor/shared` copies, and `pnpm db:generate` correctly answers "No schema changes, nothing to migrate" — verified, the migration count stayed at 11. Two consequences worth knowing: (a) do not write a migration by hand for it, and do not commit an empty generated one; (b) the flip side is that the DB will happily store a value the TS enum rejects, so rows written by a seed/SQL outside the app are not validated — `toSkillDto` casts `row.type as SkillType` without parsing. Removing or renaming a value IS a data migration, even though adding one isn't.
  Where: `src/db/schema/skills.ts:14` (`source` enum), `src/db/migrations/0000_init.sql:321` (`"source" text NOT NULL`), `src/modules/skills/helpers.ts:48` (`row.source as SkillSource`)

- **2026-09-21 · Upgrading drizzle-orm will make `pnpm arch:check` report 5 "new" violations** — The architecture baseline matches a violation by the exact `rule + from + to` triple, and for an npm package `to` is the resolved pnpm path **with the version in it**: `node_modules/.pnpm/drizzle-orm@0.38.4_postgres@3.4.9/node_modules/drizzle-orm/index.d.ts`. 5 of the 43 baselined entries look like that (the `drizzle-orm` imports in `pulls`/`settings`/`polling`/`workspace` routes), so bumping drizzle-orm or `postgres` invalidates them and the gate fails on code nobody touched. It is not a false alarm — fix those four route files (they are next in the refactoring order anyway), or re-run `pnpm arch:baseline` and check `git diff --stat` on the baseline shows the old entries replaced, never a net gain. Related CLI trap: this repo pins dependency-cruiser 17, where the baseline is written by the separate `depcruise-baseline` binary; from 18.3 it is `depcruise --baseline` and the `arch:baseline` script must change with the upgrade.
  Where: `.dependency-cruiser-known-violations.json:1` (the versioned `to` paths), `package.json:14` (`arch:baseline` → `depcruise-baseline`), `.claude/skills/backend-onion-architecture/references/enforcement.md` (the baseline section)
  **Update (2026-09-22): it fired in CI without any version bump — the `node_modules` LAYOUT is enough.** Those same 5 entries broke on the L2 branch while `pnpm arch:check` stayed green locally. `.npmrc:1` sets `node-linker=hoisted`, so a fresh CI install puts the package at the real path `node_modules/drizzle-orm/index.d.ts`, whereas a local `node_modules` created under pnpm's default isolated linker resolves it through the symlink `node_modules/drizzle-orm -> .pnpm/drizzle-orm@0.38.4_postgres@3.4.9/node_modules/drizzle-orm`. The baseline was generated on the isolated layout, the `to` strings don't match, and the gate reports `x 5 dependency violations` on untouched code. **The tell is the ignored-count, not the error text:** local says `43 known violations ignored`, CI says `38` — the 5-entry gap is the whole diagnosis, and it points at the layout, not at anyone's import. Before re-running `pnpm arch:baseline`, confirm `ls -la node_modules/drizzle-orm` is a real directory and not a symlink; if it is a symlink, `rm -rf node_modules && pnpm install --frozen-lockfile` first, otherwise you just re-commit the same CI-incompatible paths. Verify the `.npmrc` still says `hoisted` before trusting a local green run at all.
  Where: `.npmrc:1` (`node-linker=hoisted`), `../.github/workflows/server-unit.yml:72` (the `Architecture boundaries` step that surfaced it)
  **Resolved (2026-09-22): the baseline now contains ZERO `node_modules` paths, so the whole class of failure is gone.** Rather than re-baseline on the CI layout, the four route files got the `repository.ts`/`service.ts`/`compose.ts` they were owed, which removed all 5 `drizzle-orm` entries plus their 4 `db/schema.js` siblings; the baseline went 43 → 33 and `grep -c node_modules .dependency-cruiser-known-violations.json` returns 0. Every surviving entry resolves to a repo-relative `src/…` path or a node builtin (`fs`, `fs/promises`), and those are identical under either linker. **The rule to keep:** a baselined violation whose `to` points into `node_modules` is inherently machine-dependent — never accept one. If a new npm-package violation appears, fix the import; if it genuinely has to be recorded, know that the entry is only valid for whoever generated it.
  Where: `.dependency-cruiser-known-violations.json` (33 entries, all `src/…` or builtins), `src/modules/pulls/repository.ts:44` (`PullsRepository` — where the `drizzle-orm` import moved to), `src/modules/settings/repository.ts:11` (`SettingsRepository`)

## Recurring Errors & Fixes

- **2026-09-24 · `waitForPrRuns` returning `done` does NOT mean the `run_traces` row exists yet — reading the trace right after it is a race (×1)** — Observed once, non-deterministically: `reviews-skills.it.test.ts` failed with `TypeError: Cannot read properties of undefined (reading 'trace')` inside `runAndReadSkillsBlock`, then passed on two clean reruns. Root cause is a real ordering window, not flaky infrastructure: `waitForPrRuns` polls `agent_runs.status` until it is terminal (`test/helpers/runs.ts:12`), but the executor writes the run row terminal at `run-executor.ts:280` (`completeAgentRun`) and only writes the trace document 45 lines later at `run-executor.ts:325` (`saveRunTrace`). Between those two awaits the run reads as `done` while `run_traces` has no row, so `const [row] = await db.select()...` yields `undefined` and the non-null assertion `row!.trace` throws. Any test that waits on run status and then reads `run_traces` has this bug latent in it — it just needs a slow enough machine. Fix: poll for the trace row itself rather than inferring it from run status (a small `waitForRunTrace(db, runId)` alongside `waitForPrRuns`), or assert on `row` before dereferencing so the failure names the real cause. Do NOT "fix" it by widening `waitForPrRuns`'s timeout — the run is genuinely finished; it is the trace that is late.
  Where: `test/reviews-skills.it.test.ts:156` (`const [row] = …` then `row!.trace` at `:159`), `test/helpers/runs.ts:12` (`TERMINAL` — status-only wait), `src/modules/reviews/run-executor.ts:280` (`completeAgentRun`), `src/modules/reviews/run-executor.ts:325` (`saveRunTrace`)

- **2026-09-24 · `expected 'running' to be 'done'` in a `*.it.test.ts` means the test is making a REAL network call, not that the run hung (×1)** — Adding any pre-review step that resolves a feature model (L03's intent classifier: `container.featureModel(ws, 'review_intent')` → `container.llm('openrouter')`) silently gave every existing `POST /pulls/:id/review` integration test a live external dependency. Root cause: `NODE_ENV=test` does **not** stub secrets — `config.ts:74` always resolves the real `~/.devdigest/secrets.json`, so `container.llm()` builds a REAL provider whenever the key is on the box, and only an explicit `ContainerOverrides.llm[<provider>]` mock prevents the call. The failure is a **timeout, not an error**: `waitForPrRuns`'s default `timeoutMs = 10_000` against a measured ~9.1s live OpenRouter structured call means the suite flakes rather than failing deterministically — it passes on a fast network and on a machine with no key, and fails on a slow one. The tell is suite duration, not the message: the integration suite went 6.6s → 43.5s before the fix and back to 6.6s after. Fix: any `*.it.test.ts` that triggers a review must mock the provider of EVERY feature model the run touches, not just the agent's own. Same trap for GitHub — a PR body containing `#123` makes `parseIssueRef` call `container.github()`, so such a test needs a `github` override too, even though the call is best-effort.
  Where: `src/platform/config.ts:74` (`secretsPath` — real path even under test), `src/platform/container.ts:187` (`llm()`), `test/helpers/runs.ts:19` (`timeoutMs = 10_000`), `test/reviews.it.test.ts` / `test/reviews-skills.it.test.ts` (the two fixed instances), `src/modules/reviews/intent-helpers.ts` (`parseIssueRef`)

## Open Questions

- **2026-09-19 · A failed background job can crash the API** — `JobRunner.enqueue` returns a `done` promise that rejects when the job fails, every caller drops it, and `src/` has no `unhandledRejection` handler, so Node's default (crash) applies. A timed-out job is also marked `failed` while its handler keeps running. Checked: `test/repo-intel-symbol-clamp.it.test.ts:6` records a past crash of this kind. Open: `.catch` at call sites, or a process-level handler?
  Where: `src/platform/jobs.ts:96` (`done` rejects), `src/modules/repos/service.ts:98` / `src/modules/repo-intel/routes.ts:53` (dropped promises), `src/platform/resilience.ts:20` (timeout doesn't cancel)

- **2026-09-19 · The API listens on all interfaces with no auth** — `app.listen({ host: '0.0.0.0' })` plus `LocalNoAuthProvider` means any host that can reach the port can call every route, e.g. write provider keys via `POST /settings/test-connection`; CORS only restricts browsers. Open: bind `127.0.0.1` by default for local use?
  Where: `src/server.ts:29` (`host: '0.0.0.0'`), `src/app.ts:90` (CORS)

- **2026-09-19 · `RunBus` never frees memory** — `complete()` deletes only the emitter; `buffers`, `seq` and `completed` grow for the process lifetime (its doc comment says it releases buffers).
  Where: `src/platform/sse.ts:82` (`complete`), `src/platform/sse.ts:75` (the doc claim)
