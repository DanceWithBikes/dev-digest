## What Doesn't Work

- **2026-09-24 · Rewriting a spec link in the PR body as a full GitHub URL does NOT stop `resolveSpec` from trying to read it locally** — Tried: fixing the "Linked spec … could not be read" warning on a PR by replacing the repo-relative link `[docs/specs/intent-layer.md](docs/specs/intent-layer.md)` with an absolute branch URL (`https://github.com/<owner>/<repo>/blob/<branch>/docs/specs/intent-layer.md`), on the theory that the doc comment above the regex — *"No fetch, no URL — internal sources only"* — means a URL is ignored. Failed because: `SPEC_REF_RE` has no URL guard whatsoever; it is an unanchored `\b…\b` substring match, so it happily matches `docs/specs/intent-layer.md` **inside** the URL and `resolveSpec` still does `git.readFile(repo, 'docs/specs/intent-layer.md')` against the local clone. The comment describes the *intent* (never fetch a URL over HTTP), not a parsing guarantee. Two real traps follow: (a) a link to a spec in a **different repo** is silently treated as a path in *this* repo's clone — it either fails confusingly or, worse, succeeds and feeds the classifier a same-named file that has nothing to do with the PR; (b) a `/blob/<branch>/` URL pointing at a non-default branch is read from the default-branch working tree regardless (see the `git.readFile` entry below). Instead: the absolute URL is still the right thing for the human-readable PR link (a relative link 404s on GitHub until merge, because GitHub resolves it against the default branch), just don't expect it to change anything app-side — the warning is honest and stays until the file is on the tracked branch.

## Codebase Patterns

- **2026-09-24 · Only the spec attempt records "referenced nothing"; `issue` and `commits` don't have an honest empty state at all** — Tracing what a near-empty PR (title "1", no body, no linked issue/spec, real diff) actually sends the classifier surfaced three asymmetries in `RepoIntentSourceCollector.collect`: (1) `resolveIssue` returns `null` WITHOUT pushing any attempt when `parseIssueRef` finds no `#N` (`compose.ts:65`, the `if (issueNumber == null) return null` branch, no `attempts.push` before it) — unlike the spec's sibling branch, which now explicitly records `{kind:'spec', ref:null, ok:false}` for exactly this case (`compose.ts:99`). So `sources[]` has zero entries for `issue` on the vast majority of PRs, and the card has nothing to render either way. (2) `commits` is pushed `ok: true` UNCONDITIONALLY (`compose.ts:60`), even when `commitsForPull` returned an empty array — `renderCommitsDigest` degrades to the `(no commits)` placeholder in the prompt, but the provenance record still claims success. (3) Neither `renderFilesDigest` nor `renderCommitsDigest` has a character cap — `MAX_PR_BODY_CHARS`/`MAX_ISSUE_BODY_CHARS`/`MAX_SPEC_CHARS` exist in `constants.ts` for the other three sources, but a PR with many changed files (many hunks each) sends the entire files digest uncapped. None of this breaks the classifier — `Intent` (`vendor/shared/contracts/brief.ts:9`) has no `minLength`/`minItems`, so a confident-sounding `intent` still validates even when the only real evidence was file paths and commit subjects — but it does mean the ONLY honesty signal a maximally-thin PR ever produces is `"PR description is empty"`; an uninformative title, an unreferenced issue, and a diff too large to fully digest all pass silently.
  Where: `compose.ts:65` (`resolveIssue` — no attempt on the no-reference branch), `compose.ts:99` (`resolveSpec`'s sibling branch — the pattern to match if `issue` gets the same treatment), `compose.ts:60` (`commits` — unconditional `ok: true`), `constants.ts:28` (the three char caps that stop at `spec`, missing `files`/`commits`), `vendor/shared/contracts/brief.ts:9` (`Intent` — no length constraints), `reviewer-core/src/intent/filter.ts:22` (`filterByIntent` — why a wrong `out_of_scope` bullet from thin evidence can silently drop a real non-CRITICAL finding)

- **2026-09-24 · `pull_requests.body` is filled ONLY by the detail sync, so an intent derived too early reports "PR description is empty" about a PR that has one** — The PR-list import never writes `body`; it arrives once, from `pulls/service.ts:101` (`repo.updateDetail(pr.id, detail.body ?? null, …)`), on the detail fetch that the PR page triggers. The Intent Layer reads the PERSISTED body (`intent-helpers.ts:6` comment says so explicitly, and `service.ts#detectIntent` passes `pull.body` straight from `getPull`), never GitHub. So classify a PR whose detail has not synced yet — or re-run intent within seconds of editing the description on GitHub — and the body source records `ok: false`, `missing_context` gets "PR description is empty", and that text then sits in the card forever: `head_sha` cannot expire it, because editing a description moves NO commit. Observed on PR #5 (`body` = "not amazing description" in the DB, intent generated 17:32:55 still claiming it empty). Fixed by fingerprinting the classified body (`pr_intent.body_sha`, migration `0015_modern_junta.sql`) and deriving `stale` on read (`intent-helpers.ts:91` `isIntentStale`, used by `service.ts:206` for the API and `run-executor.ts:379` to decide whether a run may reuse the stored record). Two traps for whoever touches this next: (a) `bodyFingerprint(null)` returns the hash of the empty string, NOT null — null in the column means "row predates the column", and conflating the two makes "classified with no description" un-expirable; (b) the fix makes the record honest, it does not make it fresh — a stale intent is still served as-is, with `stale: true` for the UI's re-run affordance.
  Where: `../../pulls/service.ts:101` (`updateDetail` — the only writer of `body`), `../../pulls/repository.ts:104` (`updateDetail`), `intent-helpers.ts:69` (`bodyFingerprint` — total, never null), `intent-helpers.ts:91` (`isIntentStale`), `service.ts:206` (`stale` derived on read), `run-executor.ts:379` (`!isIntentStale(stored, pull)` — was `stored.head_sha === pull.headSha`), `../../../db/schema/reviews.ts` (`bodySha`)

- **2026-09-24 · `missing_context[]` is a 1:1 rendering of the failed `sources[]`, so a UI that shows both states every gap twice** — `deriveMissingContext` is `attempts.filter(a => !a.ok).map(describeMissingSource)` — exactly one message per failed attempt, no filtering, no merging. The IntentCard rendered the failed `sources[]` AND `missing_context[]` as two separate warning lists, so every gap appeared twice in different words: "body could not be read" above "PR description is empty", "spec could not be read" above `Linked spec "…" could not be read`. Rule when consuming the record: `missing_context[]` is the human-readable form and is the one to render; the raw `sources[]` are provenance (which kinds were tried), useful for a detail panel or a log line, not for a second warning list. The per-source `intent.sourceUnavailable` string is kept only as a fallback for records stored before `missing_context` existed.
  Where: `intent-helpers.ts:6` (`deriveMissingContext` — the 1:1 map), `../../../../../../client/src/app/repos/[repoId]/pulls/[number]/_components/IntentCard/IntentCard.tsx:69` (`warnings` — the dedupe), `../../../../../../client/messages/en/prReview.json:131` (`sourceUnavailable` — the fallback string)

- **2026-09-24 · Where a development plan belongs is encoded in a regex, not in any doc — `docs/plans/<feature>.md`** — `SPEC_REF_RE` accepts four shapes: `docs/specs/…md`, `docs/design/…md`, `docs/plans?/…md` and bare `plans?/…md`. So the Intent Layer was built expecting a *development plan* to be a first-class linkable source alongside the spec, even though this repo has no `docs/plans/` directory and no plan file has ever been committed (see the "plan §0/§1" entry under What Doesn't Work — the Intent Layer's own plan was an uncommitted plan-mode artifact). Consequence: put a plan at `docs/plans/<feature>.md` and a PR that mentions it gets a `spec` source for free, no code change; put it anywhere else (`PLAN.md`, `docs/plan-<x>.md`, `docs/planning/…`) and `parseSpecRef` will not see it. Note the regex returns only the FIRST match in the body, so a PR body linking both a plan and a spec resolves whichever appears earlier and silently ignores the other.
  Where: `server/src/modules/reviews/intent-helpers.ts:42` (`SPEC_REF_RE` — the `plans?` alternatives), `server/src/modules/reviews/intent-helpers.ts:46` (`body.match` — first match only, not `matchAll`)

- **2026-09-24 · Missing-context is the honesty signal; sources infrastructure gathers full materials but keeps them private** — The Intent Layer's three-phase architecture (collect → classify → derive) is strict about data flow: the collector gathers full materials (`issue.title`, `issue.body`, `spec.text` - the actual documents), but the public API only exposes metadata (`sources: [{kind, ref, ok}]`) and an honesty field (`missing_context[]` — sources that failed to resolve). This separation is intentional: (a) on success, the LLM consumed the materials and returned scope bullets; the raw content is redundant for the UI, which only needs to know which sources resolved (b) on failure, `missing_context[]` tells the user precisely which references the system tried and failed to fetch, triggering a re-run or manual fix. A future feature might expose sources content in the API (e.g., an "expand sources" detail panel in the Intent card), and the data collection infrastructure is already there — just not exposed in `PrIntentRecord`. Consequence: if you add a new source kind (e.g., linked wiki pages), the collector's `collect()` function is the right place to fetch and cache the materials; the UI can always see them later without changing classifier or repository code.
  Where: `ports.ts:92` (`collect` returns full `GatheredIntentSources`), `ports.ts:13` (`IntentSource` — metadata only), `server/src/vendor/shared/contracts/review-api.ts:76` (`sources: IntentSource[]`, `missing_context: string[]`), `compose.ts:66` / `compose.ts:89` (`resolveIssue` / `resolveSpec` fetch full bodies and cache them), `run-executor.ts:462` (only `sources.attempts` persisted as metadata)

- **2026-09-24 · `git.readFile` ignores the PR's `head_sha` entirely — it reads the clone's current working-tree file** — `SimpleGitClient.readFile` is `readFile(join(this.clonePathFor(repo), path), 'utf8')` — no `git show <sha>:path`, no checkout, no ref argument at all. So a linked spec resolves (or doesn't) based on whatever is physically checked out on disk in `server/clones/<owner>/<repo>/` at call time, NOT the specific commit the PR was opened against. Two consequences: (a) testing/demoing spec resolution for an old PR works fine even though it's "wrong" (reads today's file, not the PR-era file) — don't be surprised the content doesn't match the PR's actual diff; (b) if the local clone is stale (not `git pull`ed since some doc was added upstream), `resolveSpec` fails with a perfectly valid-looking spec path — the fix is refreshing the clone, not the code.
  Where: `server/src/adapters/git/simple-git.ts:129` (`readFile`), `server/src/adapters/git/simple-git.ts:37` (`clonePathFor`), `server/src/modules/reviews/compose.ts:96` (the only caller, `resolveSpec`)
  **Addition (2026-09-24):** consequence (b) understates it — refreshing the clone only ever helps if the spec already exists on the repo's *default branch*. `GitClient.fetchPullHead(repo, n)` (`server/src/vendor/shared/adapters.ts:207`, implemented at `server/src/adapters/git/simple-git.ts:72` — fetches `origin pull/<n>/head` into a local `pr-<n>` ref) is fully built but has **zero callers anywhere in the codebase** — grep for `fetchPullHead(` outside its own definition/interface/mock returns nothing. The clone's working tree is only ever advanced by `sync()` (`simple-git.ts:79`), called exclusively from `repo-intel/service.ts:151` (`resyncRepo`) with `repo.defaultBranch` — never with a PR's branch or head_sha. So a spec (or any file) that a PR introduces about itself has no code path to resolve before that PR merges, full stop — not a staleness problem, a missing-feature problem. Confirmed live: PR #10 referenced `docs/specs/intent-layer.md`, added by that same PR; pulling the clone to `origin/main` did not fix it because the file isn't on `main` yet. Review-run diff loading has the identical blind spot but a safety net: `loadDiff` (`server/src/modules/reviews/diff-loader.ts:20`) calls `container.git.diff(repo, pull.base, pull.headSha)` assuming `headSha` is already resolvable in the clone, with no fetch step — on failure it silently falls back to `diffFromPrFiles` (`diff-loader.ts:29`), reconstructing the diff from persisted `pr_files` patches instead of the live tree.
  **Correction (2026-09-24, same day):** the "no code path, full stop" half is now FIXED for the spec source — `fetchPullHead` has its first caller. `compose.ts#readSpecAtHead` resolves a linked spec in three steps, first hit wins: `git.readFileAt(repo, pr.headSha, path)` (new `GitClient` method, `git show <ref>:<path>` — never a checkout, the clone is a shared read-only mirror), then `fetchPullHead(repo, pr.number)` + a read off the `pr-<n>` ref it creates, then the old working-tree `readFile` as the last resort. So a PR that documents itself now resolves its own spec before merge (verified on PR #10: `git fetch origin pull/10/head:pr-10` then `git show pr-10:docs/specs/intent-layer.md` returns the file the clone's `main` worktree does not have). Two things did NOT change: `loadDiff`'s identical blind spot (still relies on `pr_files` patches as its net), and the honesty contract — when all three attempts fail, the attempt is still recorded `ok: false` and the default-branch copy is never silently substituted for a spec the PR actually changed. Note the fetch costs one network round trip per intent run whenever the head sha isn't already in the clone, which is the common case for a shallow clone.

- **2026-09-24 · "The classifier never sees diff bodies" is enforced by the PORT'S TYPE, not by discipline — keep it that way** — `UnifiedDiff` is `{ raw: string; files: [...] }` and `raw` is the ENTIRE diff text, so any function handed a `UnifiedDiff` can leak whole file contents into a prompt. The Intent Layer's guarantee is structural instead of documentary: `IntentSourceCollector.collect` takes `IntentDiffFiles` (`{ files: { path, hunks: {oldStart,oldLines,newStart,newLines}[] }[] }`), which has no `raw` at all, and the single call site passes a fresh literal `{ files: diff.files }`. Because that is an object literal, TS excess-property checking also rejects a later `{ ...diff }` shortcut — the leak becomes a compile error, not a review miss. Two things follow: (a) never "simplify" the signature to accept `UnifiedDiff` just because the caller has one (structural typing makes it assignable, which is exactly the trap); (b) hunk header TEXT is not available anywhere — `adapters/git/diff-parser.ts` keeps only the numbers, so `intent-sources.ts#renderHunkHeader` re-renders `@@ -a,b +c,d @@` from them.
  Where: `ports.ts:38` (`IntentDiffFile`), `ports.ts:51` (`IntentDiffFiles` — no `raw`), `ports.ts:92` (`collect` signature), `run-executor.ts:452` (`{ files: diff.files }` — the only call site), `../../../vendor/shared/adapters.ts:186` (`UnifiedDiff.raw`)

- **2026-09-24 · Need another module's TABLE? Query it from your own repository — do NOT look for a `container.<m>Repo`** — `modules/AGENTS.md` says "never import another module's folder — shared pieces come from `container`", which reads as "there is a container getter for every module's repository". There is not: `container` exposes `agentsRepo`, `reviewRepo`, `skillsRepo`, `repoIntel` and nothing else — notably **no `pullsRepo`**, even though `pulls` owns `pull_requests`, `pr_files` and `pr_commits`, which reviews reads constantly. The resolution is the ring rule, not a new getter: `only-repositories-touch-the-database` scopes on the *layer*, not the table owner, so a module's own `repository.ts` may SELECT from any table. L03's Intent Layer needed commit messages and added `commitsForPull` to the reviews repository rather than reaching for `pulls/repository.ts` (which `no-cross-module-imports` would have rejected) or adding a container getter (which nothing else wants). `db/AGENTS.md`'s "don't edit shared schema tables" restricts *writing/migrating* another module's tables, not reading them. Rule of thumb: cross-module **behaviour** goes through a container port; cross-module **data** is just a query in your own repository.
  Where: `repository/pull.repo.ts:115` (`commitsForPull`), `repository.ts:142` (facade), `../../../platform/container.ts:99` (`agentsRepo` — note the absent `pullsRepo` beside it), `../../../.dependency-cruiser.cjs:126` (`no-cross-module-imports`)
