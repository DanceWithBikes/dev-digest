# Spec: Eval Pipeline

Spec ID: SPEC-04
Status: implemented
Supersedes: —
Introduced in: L06

## Problem & user

A repo owner who tunes a reviewer agent in the studio (system prompt, model, linked skills) has no regression protection. One edit to the prompt can silently change what the agent finds: it can start missing a leaked secret it used to catch, or start flagging code the team has already dismissed as fine. The only way to notice today is to re-run the agent on real PRs and compare findings by eye, which nobody does. Yet the labelled data already exists: every Accept or Dismiss decision on a finding (L01–L05) says what the agent should and should not report. The cost is prompt changes shipped blind, and no way to show that a "better" prompt is actually better.

## Goals / Non-goals

Goals:
- A repo owner can turn a real, decided finding into a regression case in one click: an accepted finding becomes "must find X at file:line", a dismissed one becomes "must NOT flag Y".
- A repo owner can create and edit cases by hand, and they live in the same set and run the same way.
- A repo owner can run an agent over its whole case set with frozen inputs, so that runs of different agent versions are comparable.
- Each run produces recall, precision and citation accuracy computed purely in code, with zero model calls in scoring, and the raw counts are stored so every number can be reproduced.
- A repo owner can see run history, a trend per run, and a side-by-side comparison of two runs (metric deltas plus the system prompt diff), so that a prompt change visibly moves the metrics.
- An Eval Dashboard lists every agent with its latest metrics and the recent runs across agents.
- One root command, `pnpm verify`, proves the feature's checks are green.

Non-goals:
- Skill-owned eval sets in the product. The `skill` owner kind stays unused by this feature.
- LLM-judged scoring of any kind. Scoring matches file and line ranges only.
- Threshold-based CI gating (failing a build when recall drops below a value).
- Automatic eval runs when an agent is saved.
- A PreToolUse hook and mutation testing (out of scope for this spec).
- The skill eval for `backend-onion-architecture` under `evals/`. It is a separate artifact, listed only under Touched packages.
- Checking that a finding's cited line actually contains the problem. Citation accuracy reuses the grounding gate, which compares line ranges only, so a wrong line inside a brand-new file still counts as grounded (`reviewer-core/docs/insights.md:47`).
- Per-case runs from the studio. Cases always run as part of a whole-set batch.
- Running eval batches from the MCP server.

## User stories

- US-1: As a reviewer in the studio, I want a "Turn into eval case" button on a decided finding, so that my Accept or Dismiss decision becomes a regression case without retyping it.
- US-2: As a repo owner, I want to see every eval case of an agent on its Evals tab, with the expectation kind, the `file:start-end` and the last-run result, so that I know what the agent is held to.
- US-3: As a repo owner, I want to create and edit cases by hand (paste a diff, see a preview, set the expectation kind, file and line range), so that I can cover cases no real PR produced yet.
- US-4: As a repo owner, I want to run the agent over all its cases with frozen inputs, so that two runs differ only because the agent changed.
- US-5: As a repo owner, I want recall, precision and citation accuracy per run, computed without a model, so that the numbers are cheap, deterministic and reproducible.
- US-6: As a repo owner, I want run history, a trend chart, and a comparison of two runs with metric deltas and the prompt diff, so that I can tell whether my prompt change helped.
- US-7: As a repo owner, I want an Eval Dashboard in the sidebar listing every agent's latest metrics and the recent runs, so that I can see the state of all agents at once.
- US-8: As an operator, I want one root command that runs every check of this feature and says PASS or FAIL per lane, so that I can prove the feature is green.

## Edge cases

- A finding that is accepted and later dismissed: accept and dismiss clear each other, so the finding has exactly one decision at a time. A case already created from it keeps its original kind, and a second click returns that case (AC-33).
- The studio is reloaded after a case was created from a finding: the card shows "Turn into eval case" again, and a click returns the existing case with 200 and the "Open in Evals" link (AC-33, AC-76).
- A finding whose file has a patch but whose cited lines lie outside that patch's hunks: the case is still created (AC-26). A `must_find` case like this can never be matched by a kept finding, because the grounding gate drops any finding there.
- A stored PR patch without a `--- a/` / `+++ b/` header parses to 0 files. That is why the one-click diff adds the header (AC-26) and why the engine helper exists (AC-10).
- The review's agent was deleted after the review: the owning agent does not exist, so the API answers 404 (AC-34).
- Two `POST /agents/:id/eval-runs` requests at almost the same time: the second gets 409 `batch_running` (AC-46). An exact race between the two checks is accepted (single-user studio).
- The API restarts while a batch is running: the batch becomes `failed` on boot (AC-58). The MCP process never starts eval batches (Non-goals), so the reaper cannot hit another process's batch.
- A case is deleted while its batch is running: that case's run is not stored or is removed with it (AC-38). The batch still finishes (AC-53, AC-54).
- A case is added while a batch is running: it is not part of that batch (AC-47).
- An agent with cases but no batch yet: the Evals tab shows "No runs yet…" (AC-88), and the dashboard row shows no metrics (AC-107).
- Only 1 `done` batch: the trend chart shows 1 point (AC-89), and the metric cards show no delta (AC-87).
- Two compared batches with an identical system prompt: the prompt diff shows no changed lines (AC-95).
- A failed batch has null metrics: it appears in the run history (AC-92) but not on the trend chart (AC-89) or in the overview trend (AC-62).
- "Run all agents" while one agent has a running batch: that agent's request gets 409 `batch_running`, and the studio names it in a notification (AC-110). The other agents still run.
- The seeded model `seed` has no price: both seeded batches show cost "—" (AC-57, AC-90).
- A model that answers with invalid structured output for a case: the provider adapter's existing repair re-ask applies. If it still fails, that case errors (AC-53).
- A large manual diff: the engine may switch that case to map-reduce, which takes more than 1 model request. AC-51 assumes small diffs. A diff over 200,000 characters is rejected (AC-128).
- A batch in which every case errored: it is `failed` with null metrics (AC-55). The fallback value 1 of AC-16 to AC-18 applies only to a batch with at least 1 scored case.
- A case created from a finding always has exactly 1 expectation (AC-23, AC-24). Opening it in the Case Editor shows 1 row, whose "Remove" button is disabled (AC-130).
- The existing case editor copy in `client/messages/en/eval.json` describes a JSON expected-output editor and a "Run case" button. Those keys are obsolete and are replaced by keys for the expectation-row editor (NFR-8). No criterion checks their removal.
- The API returns metrics as raw doubles from 0 to 1. Only the studio rounds them to whole percentages (AC-86).

## Untrusted inputs

- PR patches copied into a case diff, and diffs pasted into the Case Editor: prompt injection into the reviewer prompt. Covered by AC-48: the diff reaches the engine only as its diff input, which the engine wraps as untrusted (`reviewer-core/src/prompt.ts:187`). Malformed diffs are rejected by AC-39 and AC-100. Oversized diffs are rejected by AC-128.
- PR title and body frozen into the case's input meta: prompt injection. Covered by AC-48: they reach the engine only as the PR description, which the engine wraps as untrusted (`reviewer-core/src/prompt.ts:171`).
- Finding fields copied into an expectation (LLM output from an earlier review): the file and lines are used only for exact string and range comparison (AC-11), never to read a file. The title is shown as plain text (AC-112).
- Findings returned by the model during a batch: invented paths and lines are dropped by the grounding gate and counted against citation accuracy (AC-18). They are compared, never opened (AC-11, AC-49).
- Manual case names, notes and expectation titles: Markdown or script injection into the studio. Covered by AC-112.
- Batch error messages, which may embed provider text: shown as plain text (AC-112) and kept out of logs except as status (NFR-11).
- The `agent_id` fallback in the one-click request body: a cross-workspace reference. Covered by AC-34.
- Expectation file paths: never used for filesystem access, because the eval pipeline reads no clone, repo-intel or GitHub data (AC-49), so path traversal has nothing to reach.
