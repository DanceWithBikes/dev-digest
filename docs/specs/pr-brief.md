# Spec: PR Brief

Spec ID: SPEC-03
Status: implemented
Supersedes: —
Introduced in: L05

## Problem & user

A reviewer who opens a pull request in the studio has no short answer to three questions: what the PR does and why, where it can break things, and which lines to read first. Today the Overview tab shows the Intent card, the Blast Radius card and the raw PR description side by side. The reviewer has to combine them by hand, and then read the diff from the top to find the risky parts. The verdict and PR score exist only on the Agent runs tab, and only after a full review run. The result is minutes spent orienting on every PR, and risky lines that are read late or missed.

## Goals / Non-goals

Goals:
- From the Overview tab, a reviewer can generate a brief: a short summary, risk areas (each with a title and a file) and a review focus list (`file:line — reason`).
- Every file the brief names is a file changed in this PR or a caller file from the PR's Blast radius map. The model cannot introduce a path.
- The brief states which inputs were missing, stale or truncated (intent, blast radius, specs, diff) and why, instead of silently working without them.
- A brief is generated once and then shown immediately on every later visit. It is regenerated only when the reviewer asks for it.
- One click on a review focus item takes the reviewer to that file on the Files changed tab.

Non-goals:
- Producing a verdict or PR score from the brief. These come from review runs only.
- Running the Intent classifier or rebuilding the repo-intel index as part of brief generation.
- Automatic generation or regeneration: not on page open, not on new commits, not after a review run.
- An MCP tool that reads or generates the brief.
- Populating PR history (prior PRs). The Blast Radius card keeps its own prior-PRs view.
- Highlighting the exact line on the Files changed tab. Navigation targets the file.
- Brief history. Only the latest brief per PR is kept.
- A second model call to repair invalid file references. Invalid references are dropped.

## User stories

- US-1: As a reviewer in the studio, I want a "Generate brief" button on a PR's Overview tab, so that I can get an orientation summary on demand.
- US-2: As a reviewer in the studio, I want a short summary, risk areas with a file each, and a review focus list with `file:line — reason`, so that I know what the PR does and where to look first.
- US-3: As a reviewer in the studio, I want the brief to say which inputs (intent, blast radius, specs, diff) were missing or partial, so that I know how far to trust it.
- US-4: As a reviewer in the studio, I want to click a review focus item and land on that file in Files changed, so that I go from brief to code in one step.
- US-5: As a reviewer in the studio, I want the brief to appear immediately when I come back to the PR and to be marked stale after new commits, so that I neither wait for nor pay for a regeneration I did not ask for.
- US-6: As a reviewer in the studio, I want a refresh button that regenerates the brief, so that I can update it after the PR changes.
- US-7: As a repo owner, I want the brief to use the Project Context documents I attached to my agents, so that the risks reflect our own specs.

## Edge cases

- A PR with zero changed files: the allowed path set holds only blast caller files, which may be empty. The schema then requires no focus item (AC-43), and every risk without a valid ref is dropped (AC-38). AC-45 covers the result.
- A changed file with no patch (binary, or too large for GitHub): its focus line cannot be checked against hunks and is kept as returned if it is at least 1. AC-40 applies only to files with a patch.
- A blast-only focus item while the repo's full name is not loaded: the item is shown as plain, non-clickable text. AC-79 covers the link case.
- A risk ref with a line suffix that lies outside the diff: only the path part is validated (AC-37). The suffix is shown as returned.
- Two browser tabs click Generate at once: the second request gets 409 (AC-48). Its tab shows the error with Retry (AC-65). Once the first request completes, a reload or retry shows the stored brief.
- A degraded blast map (`index_partial`, `repo_too_large`, `index_failed`) that still lists some callers: those callers count as allowed paths (AC-36), and a `missing` entry is added (AC-21). With `flag_off` or `no_data`, the map has no callers to add.
- Intent stored for an older head SHA: it is used and flagged as stale (AC-19), and no new classification is made (AC-12, only one model request).
- An agent is disabled after its documents were attached: its documents are not collected (AC-23). A skill disabled globally behaves the same.
- A single attached document larger than 20,000 estimated tokens is never sent and always appears as a `specs` missing entry (AC-27, AC-28).
- The PR has new commits after generation: the cached brief is shown with the stale badge (AC-62) and is not regenerated (AC-15).
- A model output fails schema validation: the provider adapter's existing re-ask applies. If no valid output results, AC-46 applies.
- The PR is deleted: its stored brief is deleted with it.
- A stored brief written before a contract change cannot be parsed: OQ-6.

## Untrusted inputs

- PR title and body (author-controlled on GitHub): prompt injection into the brief prompt. Covered by AC-33, AC-34, AC-35 and the length cap in NFR-4 / OQ-2.
- Patches: prompt injection through code and comments, and oversized payloads. Covered by AC-31, AC-33, AC-34 and AC-35.
- Stored intent text (earlier LLM output derived from PR text): a second-order injection. Covered by AC-33 and AC-35. Stale content is flagged by AC-19.
- Blast radius symbol and caller names (taken from repo code): injection through names. Covered by AC-33. Paths are used only as allow-list members (AC-36).
- Project Context documents (repo files at the PR head, editable by the PR author): prompt injection and size. Covered by AC-27, AC-33, AC-34 and AC-35.
- Model output paths and lines: invented or out-of-PR paths, which become in-app and GitHub links. Covered by AC-36 to AC-42.
- Model output text (summary, titles, explanations, reasons): Markdown or script injection into the studio. Covered by AC-80.
- Missing-data reasons that embed document paths (the paths come from attachments that were validated at save time by SPEC-01): rendered as plain text by AC-80.
